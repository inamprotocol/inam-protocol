## What's actually done and verified, phase by phase

### Phase 1 — Hardening
D1 compare-and-swap fixes for receipt countersign/dispute, agent registration race fix, rate limiting (both runtimes), CORS policy, D1 foreign-key enforcement, reputation O(receipts) cost-amplification fix, real Worker test suite via `@cloudflare/vitest-plugin`.

### Phase 2 — Public protocol
GitHub org `inamprotocol` / repo `inamprotocol/inam-protocol` (public, Apache-2.0). `docs.inamprotocol.org` (rendered SPEC.md + Redoc API reference). `openapi.yaml`, versioned CHANGELOG.md with per-package sections. Root domain `inamprotocol.org` deployed (content-first landing page, `site/`) as part of this track's follow-through, though it happened later chronologically.

### Phase 3 — Job resource (SPEC.md §3)
`open → accepted → completed/cancelled`, offers as a separate table (avoids concurrent-offer races), receipt↔job consistency checks. All three runtimes, all SDKs.

### Phase 4 — External identity link challenges (SPEC.md §2.1)
`agentpass_id`/`aitp_id`/`passport_id` require a signed challenge (Ed25519 or P-256) proving control of the claimed key before linking; `a2a_endpoint` unaffected. Wire format aligned with ATTP (`draft-sharif-attp-00`, real IETF draft, confirmed via research — not assumed). A real cross-language bug was found and fixed here: Python's raw ECDSA P-256 signing didn't canonicalize to low-S, so it verified against the TS/Worker side only ~50% of the time; fixed with a regression test guarding it.

### Verification v0.1 (SPEC.md §12)
A single independent verifier's signed attestation that a finalized receipt's output satisfies its job's requirements. Scope locked with the user before implementation: one verifier per verification, `provider != verifier` enforced, only `deterministic`/`agent_attestation` methods, no new dispute mechanism (reuses the existing receipt dispute state — verified reputation contribution disappears automatically the instant a receipt is disputed, since reputation computation only iterates non-disputed `finalized` receipts). Reputation gets a weight boost + new `attestedReceipts` component, no second event ledger. All three runtimes; Worker port was done by a background fork while the Python SDK was built in parallel in the main session, then integrated and reviewed. Real cross-language proof: a receipt drafted in Python, finalized in TypeScript, then independently verified by a third TypeScript identity — live run showed `attestedReceipts` 0→2 and `trustScore` 8.7→12.4. D1 migration applied to production, Worker deployed, full smoke-test suite green against `https://api.inamprotocol.org`.

- **2026-08-25/26: an external audit found 15 issues; #1-#10 are fixed, 5 remain.**
  - **#1 (critical, live) — fixed & republished.** `score: 1.0` submitted via the Python SDK failed `INVALID_VERIFICATION_SIGNATURE` (server is always TypeScript; Python's `json.dumps` and JS's `JSON.stringify` disagree on number formatting for ordinary values). Live-reproduced before/after. `sdk-js@0.3.1`/`sdk-python@0.4.1` on npm/PyPI.
  - **#2 (P0) — fixed.** Node/Worker request-validation parity: the Worker only checked required fields were *present*, never valid (a signed `{"result":"banana","score":999}` passed on the Worker, was rejected by Node). Fixed by extracting every Zod schema into `sdk-js/src/core/schemas.ts` (one shared source, not two copies) and wiring both runtimes to it. Also fixed while in the same area: malformed JSON returned 500 instead of 400 on both runtimes (confirmed live, now 400 `INVALID_JSON` on both).
  - **#3 (P0) — fixed, SPEC.md bumped to v0.6, then corrected and completed at v0.10.** Verifier independence: self-verification guard excluded only the provider, not the requester (who could name itself "independent verifier" after already approving the same work); an unregistered `verifier` was never checked; the same verifier could submit contradictory `verified`+`rejected` records for one receipt. First two closed at v0.6 — requester now excluded too, new `VERIFIER_ALREADY_DECIDED` for a second decision. **The v0.6 "verifier must be a registered agent" check was itself insufficient — caught by the user, not the original audit**: registration is free and self-service, so it never restricted who could verify, only that they'd registered first, making verifier *count* meaningless as an independence signal. Corrected at v0.10: verifier eligibility is now an explicit operator grant — new `isAuthorizedVerifier` flag on `AgentRecord`, `false` by default, settable only by a single registry-configured operator identity (`INAM_OPERATOR_DID`/`OPERATOR_DID`, unset by default = locked down) via new `POST /agents/:id/verifier-status`; `submitVerification` now checks this flag (`VERIFIER_NOT_AUTHORIZED`), a non-operator grant attempt gets `NOT_OPERATOR`. New SDK methods (`setVerifierStatus`/`set_verifier_status`) in both languages. Live-proven end to end with a real operator keypair against a running server. Deliberately not done: a DB-level FK on `verifications.verifier` in `worker/schema.sql` — live-DB migration risk judged not worth it when the application-level check gives the same protection; flagged as a real follow-up. Also not done: operator succession/rotation/multi-operator support — a single static operator key is the deliberate v0.10 scope.
  - **#4 (P0) — fixed, SPEC.md bumped to v0.7.** Reputation inflation via future-dated receipts: the decay formula had no bounds on `result.completedAt`, so a future date produced a decay factor >1 (unboundedly more trust for claiming completion further in the future) instead of being rejected. Fixed: new `INVALID_TIMESTAMP` check (>5min future or before `createdAt`), strict ISO date-format validation (verified compatible with both TS's and Python's differing timestamp formats, live-tested with the real Python SDK), and decay clamped to `[0,1]` as defense for pre-existing data.
  - **#5 (P1) — fixed, SPEC.md bumped to v0.8.** Provider/requester score conflation: reputation is entirely role-blind, so two brand-new counterparties finishing one receipt get identical aggregate reputations regardless of role (live-reproduced: `examples/starter-agents.ts` still shows both at `trustScore: 8`). Deliberately did NOT build the audit's full proposed model (first-class `providerScore`/`requesterScore`/`verifierScore` — that's real scoring-model design work, P1 in the audit's own priority table, and `verifierScore` specifically overlaps with the already-deferred Verification v0.2 backlog). Instead added purely additive `components.asProvider`/`asRequester` (same weighting as the aggregate, filtered by role) so the signal is at least visible. Also documented (not renamed, since it's a live field): `verifiedReceipts` means finalized not independently-verified, and the ~80 asymptotic ceiling on `trustScore` without live staking.
  - **#6 (unranked in the audit's own P0/P1/P2 table, done in numbered order) — fixed, SPEC.md bumped to v0.9.** Reputation-boost exploit: `hasVerifiedAttestation` counted "at least one verified" among a receipt's Verifications, so a single verifier's `verified` outvoted any number of independent `rejected` records from other verifiers (1 verified + 9 rejected still counted as attested). Tightened to require verified to strictly outnumber rejected. **Explicitly stayed inside a previously user-agreed scope boundary**: this is a narrow anti-exploit tiebreak, not the "multi-verifier consensus" mechanism the user agreed to defer to v0.2 before Verification v0.1 shipped (CHANGELOG v0.5) and that SPEC.md §12.7 still lists as backlog — no verifier-trust weighting, no quorum, no new state added. Live-reproduced end to end (real server, real SDK, 3 verifiers).
  - **#7 (P1) — fixed, SPEC.md bumped to v0.11.** Currency conflation: `GET /agents/:id/reputation` summed every finalized receipt's `settlement.amount` into `components.volumeUsd` regardless of `settlement.currency` (1000 TRY added 1000 to a USD-labelled field, next to 25 USDC). `settlement.amount`/`currency` and a job's `budget` were also unvalidated strings — `{ "amount": "banana" }` reached the reputation math and `Number("banana")` → `NaN` poisoned the volume sums. Fixed without INAM taking on any FX/settlement role (stays out of scope, §10): new `components.volumeByCurrency` map (bucketed by normalized currency, never converted or cross-summed), `volumeUsd` redefined as exactly the `"USD"` bucket (a stablecoin like USDC is its own bucket, not USD), same split on `asProvider`/`asRequester`; `amount`/`currency` now regex-validated at the shared schema layer (`VALIDATION_ERROR`), with a non-finite/negative-amount guard in the computation as backstop for non-conformant-registry data. New shared `sdk-js/src/core/settlementVolume.ts` used by both runtimes. No DB migration (compute-only). Live cross-language proof: Python SDK drafted USD/TRY/USDC receipts against a running Node server → `volumeUsd` 100 (not 1125.5), `volumeByCurrency` `{USD:100,TRY:1000,USDC:25.5}`, lowercase normalized, malformed amount rejected 400. Versions: reference server/Worker 0.6.4→0.6.5, sdk-js 0.3.2→0.3.3 (type only), sdk-python unchanged.
  - **#8 (P1) — fixed, SPEC.md bumped to v0.12.** Replay/idempotency hardening: the signed-request string (`METHOD\npath\ntimestamp\nsha256(body)`) doesn't cover the `Idempotency-Key`, so a captured signed request replayed with a *fresh* key re-verified and missed the `(caller, key)` idempotency cache → duplicate side effect (clearest on `POST /jobs`) for the whole 5-min skew window. Fix (non-wire-breaking, SDKs untouched): `requireIdempotencyKey` in both runtimes now binds each verified signature to the one key it was first seen with and rejects the same signature + different key as `REPLAYED_REQUEST` (409); Node keeps it in a new `signatureReplayCache` (TTL = skew window), Worker in the KV namespace under a `replay:` prefix. Also: idempotency now caches **2xx only** (a transient 5xx/429 no longer pins the key), and the Node in-memory caches got TTL eviction + a bounded sweep (were unbounded). No DB migration. Live replay proof against a running Node server. Versions: server/Worker 0.6.5→0.6.6, sdk-js/sdk-python unchanged.
  - **#9 (P1) — fixed, SPEC.md bumped to v0.13.** External-identity verification depth: the `linked` map presented every external identity identically — a consumer couldn't tell an `a2a_endpoint` (bare URL, INAM-signed only) from a challenge-verified `agentpass_id`/`aitp_id`/`passport_id`, and the registry didn't even record which key a challenge proved or when. Fixed additively with a new `linkedProof` map on the agent record (`{ method: "key_possession" | "unverified_claim", verifiedAt, keyType?, externalPublicKey? }`), returned everywhere incl. `GET /agents/:id/protocols`. Deliberately does **not** add live cross-registry resolution (still out of scope, §10) — it makes the current (shallower) assurance level legible instead of leaving it to a doc paragraph. New Worker D1 column `linked_proof` → **`worker/migration-add-linked-proof.sql` must run against production D1 before deploying v0.6.7 Worker code** (same as the #3 verifier-status migration; `rowToAgent` tolerates the missing column on read, but `insertAgent` names it). `updateAgentLinked`→`updateAgentLinks` in worker db. Live cross-language proven (Python SDK against Node server). Versions: server/Worker 0.6.6→0.6.7, sdk-js 0.3.3→0.3.4 (types only), sdk-python unchanged.
  - **#10 (P1) — fixed, SPEC.md bumped to v0.14.** Key management: INAM had none — an INAM ID *is* its Ed25519 key, so a compromised/lost key left an identity permanently exposed or stranded. Added the minimal safe primitive: SPEC §2.2 `POST /agents/:id/revoke` *(signed, self)* — a one-way self-signed tombstone. Revoked ID → `revokedAt`/`revocationReason`, rejected from every further signed op (`AGENT_REVOKED` 403, enforced inside `requireSignedRequest` so it covers all signed routes with one check), dropped from `GET /agents/search` (`?include_revoked=true` opts in), flagged `revoked` in reputation. Finalized-receipt history untouched. **Deliberately NOT key rotation** (signed successor-chain + reputation migration) — deferred (§10). New `client.revoke()` in both SDKs. New Worker D1 columns `revoked_at`/`revocation_reason` (`worker/migration-add-revocation.sql`). Live cross-language proven. Versions: server/Worker 0.6.7→0.6.8, sdk-js 0.3.4→0.3.5, sdk-python 0.4.2→0.4.3.
