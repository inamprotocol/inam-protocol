# Trust dimensions v0.1 sketch — a "Phase 7"-style idea

Status: **exploratory idea, not scoped, not scheduled.** This is a step earlier than the Verification v0.2 backlog (`docs-design/verification-v0.2-backlog.md`), which is *scoped-but-not-started* — concrete field shapes, ordered open questions, a recommendation on the hard tradeoff. This document is not that. It's a sketch of a third-party review comment worth not losing, written down so it doesn't have to be re-derived from scratch if the maintainer wants to pick it up someday. Phase 5 (adoption) is the current priority per the maintainer's own direction this session; nothing here competes with that or implies otherwise. No code changes accompany this document.

## The idea, stated plainly

Today `GET /agents/:id/reputation` returns one blended `trustScore` (0-100) plus a `components` object that justifies it (SPEC.md §5.3). A third-party review of this project raised the idea that a more expressive registry could let a caller reason about *multiple separate trust dimensions* — something like reliability/completion rate, verification coverage, dispute rate, counterparty diversity, economic volume, and identity confidence from linked external identities — rather than forcing everything into one blended number before the caller ever sees it.

## What's already implicitly there vs. what's genuinely new

Looking at the actual `components` object returned today (SPEC.md §5.3, computed in `src/services/reputationService.ts`) against the review's suggested dimensions:

| Suggested dimension | Already present today, as-is? |
|---|---|
| Reliability / completion rate | Close: `successRate` (weighted, decayed, counterparty-trust-adjusted — not a raw ratio) already exists as its own field. A caller filtering or sorting on `successRate` alone, ignoring `trustScore`, could already do a rough version of this today by reading `components.successRate` directly from the existing response. |
| Verification coverage | Close: `attestedReceipts` (SPEC.md §12.5, added in Verification v0.1) already reports the count of an agent's finalized receipts backed by at least one `verified` Verification. Comparing it against `verifiedReceipts` (the finalized-receipt count) already gives a rough coverage ratio today, just not computed and returned as a ratio. |
| Dispute rate | Partially: the reputation response carries an `in_dispute` flag (boolean) when `disputedCount > 0` (`reputationService.ts` line 120), but not a *rate* — there's no `disputedReceipts` count or ratio in `components` today, only a yes/no flag. This would be genuinely new as a first-class numeric field, though the underlying data (`all.filter(r => r.status === "disputed").length`, already computed as `disputedCount` inside the function) is one line away from being exposed. |
| Counterparty diversity | Partially: `flags` can already contain `concentrated_counterparty:<id>` (§5.2's 60%-of-receipts heuristic), which is a diversity signal in negative/threshold form, not a continuous score. A real diversity *dimension* (e.g. something like a normalized entropy over `pairCounts`, which the function already builds as a `Map` at line 54) would be genuinely new — the raw ingredient (`pairCounts`) exists in the function already, but nothing today turns it into a reportable number.
| Economic volume | Already fully present: `volumeUsd` is already its own top-level `components` field today, summed directly from `settlement.amount` across an agent's finalized receipts (`reputationService.ts` line 102). Note this is unverified/self-reported volume, not settlement-confirmed — see `docs-design/economic-layer-v0.1-scoping.md` §1 for that caveat, which applies here unchanged. |
| Identity confidence (from linked external identities) | Genuinely new: nothing in `computeReputation` today reads an agent's `linked` map (SPEC.md §2, populated via the §2.1 challenge-response flow) at all. This would need actual new logic — presumably something like: more challenge-verified links, especially links proven via cryptographic proof-of-control (§2.1) rather than the older unverified `a2a_endpoint`-style linking, count for more. This is the one dimension on the review's list with no existing partial implementation to build from. |

Net: three of six suggested dimensions (reliability, verification coverage, economic volume) are already fully or mostly present as individual fields a caller could read today without any change — the "multi-dimensional" framing partly already exists, just undersold, since the API response bundles them together with `trustScore` rather than foregrounding them as a callable menu. Two (dispute rate, counterparty diversity) have their raw ingredients computed internally already but not exposed as standalone reportable numbers. One (identity confidence) would need genuinely new logic against a part of the data model (`linked`) the reputation function doesn't currently touch at all.

## The real design tension

`GET /agents/search?capability=&min_reputation=&supports=` (§6) filters on a single numeric threshold today. That's the crux of the tension: a single blended score is easy to act on programmatically (`min_reputation=50`, done) precisely because it has already made the weighting decision for the caller. Multiple exposed dimensions are more honest about what's actually known and avoid forcing every caller into one project's opinion about how reliability should trade off against volume or dispute history — but a caller doing automated filtering needs *some* single decision boundary to act on, and "here are six numbers, you figure out the cutoff" pushes real work onto every consumer, most of whom will not want to think about it and will just want a working filter.

Two ways this tension could resolve, sketched without committing to either:

1. **Keep one blended default score for filtering; expose dimensions as an additional detail view.** `min_reputation=` keeps working exactly as it does today, unchanged — `trustScore` stays the one number simple callers filter on. `GET /agents/:id/reputation`'s existing `components` object already carries several of these dimensions today (per the table above); this path would mean deliberately promoting the remaining ones (a real `disputeRate`, a real diversity number, an identity-confidence number) into that same object rather than inventing a new endpoint or response shape. Low API-surface cost — no new resource, no new query semantics — but it doesn't let a caller *filter search results* by, say, "verification coverage only," only *inspect* an already-fetched agent's breakdown after the fact.
2. **Let the caller supply their own weighting.** Something like `GET /agents/search?weights=reliability:0.6,disputes:0.2,volume:0.2` (illustrative shape only, not a proposal) that computes a caller-specific blended score at query time instead of a registry-fixed one. More expressive and puts the weighting decision where it arguably belongs (with the party deciding what they need trust *for* — a low-stakes chat-support job cares about different things than a high-value contract), but meaningfully more complex to spec and implement: it changes `min_reputation` from a stored/derived-once value to a parameterized computation, raises questions about which dimensions are even weightable (probably not all six symmetrically), and reopens the auditability principle SPEC.md §5.2 currently guarantees ("a registry MUST NOT report `trustScore` without also reporting the `components` that justify it") for an arbitrary number of caller-chosen weightings instead of one canonical one.

Both are sketches, not a decision. A third option not explored in depth here — some hybrid, e.g. a small number of registry-blessed named presets (`"reliability-weighted"`, `"volume-weighted"`) rather than fully free-form caller weights — sits between the two and would need its own tradeoff analysis if this ever gets picked up.

Purely so the idea isn't lost between now and whenever (if ever) it becomes relevant. It is explicitly **not** next in line — Phase 5 (adoption, per STATUS.md's phase table and this session's direction) is still the priority, and nothing in this document should be read as a suggestion to reprioritize toward it.
